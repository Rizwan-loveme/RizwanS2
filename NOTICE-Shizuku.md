# Shizuku notice

The `:shizuku` module (part of every build since step 8F: the `includeShizuku` switch is on by default, `-PincludeShizuku=false` leaves it out; **nothing of it has ever been built or run**, the first CI run decides; steps 3 - 8 are written and statically checked: Gradle side, manifest merge, host-package patches, Start menu / Home / `rizwans2://shizuku` hooks, the `:mika` hook-up and the CI checks, see `shizuku/README.md`) is the Shizuku manager app with its server, starter and shell parts from https://github.com/RikkaApps/Shizuku
(pinned in `shizuku/UPSTREAM_VERSION` / `shizuku/UPSTREAM_COMMIT`: **v13.6.0**, commit `2650830c5b099ae0dd34fedf614d4f592ca05d65`) by RikkaW and the Shizuku contributors,
together with its `api` submodule https://github.com/RikkaApps/Shizuku-API (pinned in `shizuku/UPSTREAM_API_COMMIT`: `510fc988c02c3475d8c25db170f96792f105bdf8`, API 13.1.5).
The source is **not** stored in the project zip: `shizuku/tools/fetch-upstream.sh` clones exactly these commits into `shizuku/upstream/` before every build, so the corresponding source of the
shipped code is always the pinned upstream plus the changes listed below.

Changes made for Win11 (Apache-2.0 section 4 "state changes"), all done by `shizuku/tools/patch-upstream.py` on the pinned checkout, nothing hand-edited; also listed in `shizuku/README.md`:
- the hard-coded manager package `moe.shizuku.privileged.api` (a run-time string) is replaced by the host package of this app in 5 places: `ServerConstants`, `ServiceStarter`, `ShizukuShellLoader`, native `starter.cpp` and `ShizukuProvider` of Shizuku-API (the four other uses of the name in the nine places of upstream, `ShizukuService`, `ServiceStarter`, `ShizukuManagerProvider` and `ShizukuProvider`, are the binder extra key `moe.shizuku.privileged.api.intent.extra.BINDER`, which stays unchanged so that other Shizuku client apps keep working);
- pairing service (step 5E): two methods are added to the manager's `AdbPairingService.kt`, `onTimeout(startId)` and `onTimeout(startId, fgsType)`, each calling `stopForeground(STOP_FOREGROUND_REMOVE)` and `stopSelf()`: the service is a short foreground service and Android 14+ crashes the process if it does not stop at the time limit (here the manager runs in the main process of the app); the patch self-check fails if they are not there;
- direct boot (step 5F): `android:directBootAware` is removed from the five manager components that carry it (`BootCompleteReceiver`, `ShizukuReceiver`, `ShizukuManagerProvider`, `RequestPermissionActivity`, `ShellRequestHandlerActivity`; the last two were found on the real source in step 5G), and the `LOCKED_BOOT_COMPLETED` intent filter is removed from `BootCompleteReceiver` (its `BOOT_COMPLETED` filter stays): upstream starts its own app process before the first unlock, here that process is the main process of the whole app, which was never started in direct boot before; the result is that Shizuku's boot start runs after the first unlock; the patch self-check and the merged-manifest checker fail if a flag or the action comes back;
- night mode (step 5G): upstream sets AppCompat's process-wide default night mode from `ShizukuApplication.onCreate` and from its Settings screen; here that would force Shizuku's choice (Light / Dark) on every screen of the host. The patch removes both calls and applies the stored setting per activity instead (`AppActivity.attachBaseContext` sets `delegate.localNightMode` before `super`, inside try / catch); the patch self-check fails if a call of the process-wide setter comes back;
- intent actions (step 5D, no edit needed): `<host>.intent.action.REQUEST_PERMISSION` (the server builds it from the host package and aims it at it; the manager activity declares it as `${applicationId}.intent.action.REQUEST_PERMISSION`) and `REQUEST_AUTHORIZATION` (no sender, manifest only) follow the host; `rikka.shizuku.intent.action.REQUEST_BINDER` and the API provider's `moe.shizuku.api.action.BINDER_RECEIVED` are kept as upstream has them; the patch self-check fails if any of this changes;
- the manager application module becomes a library: `ShizukuApplication` is an `object` (the host `Application` calls it), `Context.application` / `BuildConfig.APPLICATION_ID` adapted, library manifest without `<application>` attributes and without the LAUNCHER filter (`MainActivity` not exported), activities carry their theme;
- four styles that override AppCompat / Material Components styles by name are removed (they would restyle the whole app);
- all resources get the prefix `sh_` (ViewBinding classes `Sh...Binding`), ids and the two Shizuku attrs are kept;
- the class `rikka.shizuku.manager.ShizukuLocales` (list of languages of the language setting) is generated by the patch script in the checkout. Upstream gets it from the Gradle plugin AutoResConfig by RikkaApps (MIT, https://github.com/RikkaApps/AutoResConfig), which cannot run in a library module; the script follows the same rules (language folders of the manager's `res/`, `zh-CN` / `zh-TW` shown as `zh-Hans` / `zh-Hant`) and does not copy the plugin's code;
- Gradle build files of our own (`shizuku/build.gradle.kts` = the `:shizuku` library, `shizuku/modules/<name>/build.gradle.kts` for `aidl`, `shared`, `api`, `provider`, `common`, `shell`, `rish`, `server-shared`, `starter`, `server`, and `shizuku/modules/after-fetch.gradle.kts`) replace upstream's Gradle files, which are not used. They only point Gradle at the pinned upstream sources (read from `shizuku/upstream/`, nothing is copied into the project), build upstream's own CMake files unchanged (`libshizuku.so`, `libadb.so`, `librish.so`) and list the libraries with upstream's versions (two lifted down to the versions this project already uses, see `shizuku/README.md`). Small files of ours next to them: `shizuku/consumer-rules.pro` (keep rules taken from upstream's `manager/proguard-rules.pro`), `shizuku/modules/provider/consumer-rules.pro` (copy of Shizuku-API's 5-line `consumer-rules.pro`, MIT), `shizuku/modules/shell/proguard-rules.pro` (upstream's `shell/proguard-rules.pro` plus `dontwarn` lines) and the minimal manifest of `:shizuku-shell` (an application module only because it must produce one `classes.dex`).
- the Rikka AppCompat fork (`dev.rikka.rikkax.appcompat:appcompat`, a modified AndroidX AppCompat) that upstream's manager uses is **not** used: it is excluded (in `:shizuku` and in `:app`) and the stock AndroidX AppCompat takes its place (same class names, so both cannot be in one APK);
- the Maven artifacts `dev.rikka.shizuku:api` / `provider` (13.1.5, MIT) that `:mika` asks for are **not** used when Shizuku is in the build: the root `build.gradle.kts` replaces them (and `aidl` / `shared`) by the local `:shizuku-api` / `-provider` / `-aidl` / `-shared` modules, which are the same API version built from the pinned Shizuku-API commit with the host-package patch (two copies of the same classes cannot be in one APK);
- `:app` packs no `META-INF/versions/**` resource files when Shizuku is in the build (the multi-release files of the BouncyCastle jars; Android does not read them).
- the two `tools:node="remove"` markers on `${applicationId}.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` (a `<permission>` and a `<uses-permission>`) of upstream's manifest are deleted by the patch script (step 4C-1): upstream is an application and removes what AndroidX core adds, here the library's marker would remove the permission from the whole app. The patch stops with a message if upstream's manifest no longer has exactly these two markers;
- Mika's provider `rikka.shizuku.ShizukuProvider` (same authority as the manager's `ShizukuManagerProvider`) is removed from the merged manifest by our own overlay file `app/src/shizuku/AndroidManifest.xml` (step 4B-2); it is wired only when `:shizuku` is in the build. The manager's provider is a subclass of that class, so no code path is lost.
- two Gradle plugins by RikkaApps are applied at build time, both MIT: Hidden API Refine (https://github.com/RikkaApps/HiddenApiRefinePlugin, Copyright (c) 2021 Kr328 & RikkaW; rewrites calls to hidden Android APIs) and MaterialThemeBuilder (https://github.com/RikkaApps/MaterialThemeBuilder, Copyright (c) 2022 RikkaW; generates the `Theme.Material3.*.Shizuku` styles, which end up as resources in the APK). The `rish_shizuku.dex` asset is built from upstream's `shell` project by R8 at build time.

- step 3 (3A - 3H, Gradle side): `:app` depends on `:shizuku`, and the local patched API modules replace the Maven `dev.rikka.shizuku` artifacts for `:mika`. Not built (no Gradle run was possible), see `shizuku/README.md`, "First CI run: what to look at" and "9A".
- step 4 (manifest merge, rows 4A - 4G-2): one provider with the authority `${applicationId}.shizuku` (Mika's `rikka.shizuku.ShizukuProvider` is removed by a build-type manifest overlay of `:app`, our own file), the permission ownership described in the next section, the merged-manifest checker. Statically checked, **not built**.
- step 5 (host package, patches 5B - 5G): the changes listed above (pairing service, direct boot, night mode, intent actions, binder key kept).
- step 6 (hooks, our own code in `:app`, no Shizuku source copied): `ShizukuLauncher.kt` opens the manager; it is an item of the Start menu "All apps" list, an icon of the Home screen, the link `rizwans2://shizuku` and a line of the terminal theme's list; `App.onCreate` calls `ShizukuApplication.onCreate` once in the launcher process (upstream's Application work, which the built-in boot receiver needs).
- step 7 (`:mika` hook-up): Mika's patch script (`mika/tools/patch-upstream.py`) writes the host package into Mika's `<queries>` entry for the Shizuku app and into `ShizukuController.SHIZUKU_PACKAGE` when `:shizuku` is in the build (the stock name otherwise); these are changes to Mika's source and are also listed in `NOTICE-Mika.md`, section "Shizuku hook-up". ## Permissions, who declares what (written in step 4G-1, re-read in step 9A)

With `:shizuku` in the build (the default since step 8F; `-PincludeShizuku=false` leaves it out). Everything here was read from the real manifests of Shizuku v13.6.0 and Mika 0.1.52 (patched), from `app/src/main/AndroidManifest.xml` and from the patch scripts, and is checked by rules: the patch self-check (`shizuku/tools/patch-upstream.py`, rules of steps 4C-2 / 4C-3) on the generated manager manifest and `shizuku/tools/check-merged-manifest.py` (rules of step 4E-3, 4E-4a, 4E-4b) on the merged manifest. **No merged manifest of a real Gradle build has been seen yet**; the first CI run confirms it (`python3 shizuku/tools/check-all.py --require-real`). Not legal advice.

**Declared once, by `:shizuku` (the library manifest of the manager). Neither `:app` nor `:mika` declares them.**

| `<permission>` | Level | Why the name is kept |
|---|---|---|
| `moe.shizuku.manager.permission.MANAGER` | `signature` | The server's `BinderSender` and every Shizuku client use exactly this name. Only an app signed like the declaring app can hold it; the host is both. |
| `moe.shizuku.manager.permission.API_V23` | `dangerous`, group `moe.shizuku.manager.permission-group.API` | The runtime permission that every Shizuku client app (including `:mika`) asks for. The group is declared next to it (`permission-group`, the only new element of this kind in the merged manifest). |

**What the host app (`com.srizwan.win11`, the manager itself) requests.**
- `MANAGER`: requested exactly once, by the `<uses-permission>` of the manager manifest (it merges into the app). This is what lets the server send the manager its binder. The merged-manifest rule `4E-3 manager request` checks it.
- `API_V23`: **not requested.** The host is the manager, the server treats it as always allowed. The manager manifest keeps a `<uses-permission android:name="moe.shizuku.manager.permission.API_V23" tools:node="remove"/>` as a **guard** (a marker that removes the request): if any library of the build brings the request back, the merger drops it. Two things keep it out today: this guard, and `shizukuIgnored = manifest` on `:shizuku-provider`, whose own manifest (Shizuku-API's, with the `API_V23` request) is not merged. The merged-manifest rule `4E-3 no API_V23 request` fails if a request is found.
- Consequence of the unmerged API manifest: the host also carries no `<meta-data moe.shizuku.client.V3_SUPPORT>`. It is read only for *other* apps (the server and the authorization screens), not for the manager.
- `:mika` does not declare or request any Shizuku permission itself (none of its 30 permissions is one). Before `:shizuku` it got the `API_V23` request from the Maven `dev.rikka.shizuku:api` / `provider` artifacts; with the switch on those are replaced by the local modules (see the changes above), so the request disappears with them. With the switch off nothing changes: the Maven artifacts are used as before.

**The removed markers (a change to upstream, see the list above).** The two `tools:node="remove"` markers on `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` are deleted. AndroidX core's own `<permission>` and `<uses-permission>` of `${applicationId}.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` therefore stay in the merged manifest, as they do in the app without Shizuku; `ContextCompat.registerReceiver(..., RECEIVER_NOT_EXPORTED)` needs them on Android 8 - 12 (minSdk 26). Rule `4E-3 dynamic receiver`.

**Other permission names in the manager's manifest (nothing declared by us).** `android.permission.INTERACT_ACROSS_USERS_FULL` (a system permission) protects the manager's provider and `RequestPermissionActivity`. `moe.shizuku.manager.permission.API` protects `LegacyIsNotSupportedActivity` and is declared by nobody: an upstream quirk that leaves the activity startable only by the system; it is kept as upstream has it. `ShellRequestHandlerActivity` and the two exported receivers have no permission, as upstream.

**`<uses-permission>` that more than one module asks for (identical, merge to one each; step 4C-4a).**

| `android.permission.` | `:app` | Mika | `:shizuku` | Note |
|---|---|---|---|---|
| `RECEIVE_BOOT_COMPLETED` | yes | yes | yes | three `BOOT_COMPLETED` receivers, order undefined and harmless (4D-3) |
| `FOREGROUND_SERVICE` | yes | yes | yes | enough for the manager's `shortService` pairing service (no type-specific permission needed) |
| `POST_NOTIFICATIONS` | yes | yes | yes | |
| `INTERNET` | yes | yes | yes | |
| `WRITE_SECURE_SETTINGS` | yes | yes | yes | all three with `tools:ignore="ProtectedPermissions"`; granted by hand over ADB, one grant serves all |

**`<uses-feature>` from `:shizuku` (step 4C-4b).** `android.hardware.touchscreen` and `android.software.leanback`, both `required="false"`. They are not new to the merged manifest (`:mame`, `:ppsspp`, `:retroarch`, `:tui` declare them the same way), `:app` declares none, and `required="false"` can only widen who may install, never hide the app from a device.

**Not changed by Shizuku.** The foreground-service types of `:app` (`dataSync`, `mediaPlayback`, `mediaProjection`, `microphone`) and Mika's `specialUse` stay on their own services; the manager's `AdbPairingService` is `shortService`. Fixed in step 5E (see the list of changes above): that service had no `onTimeout` (a crash risk after about 3 minutes on Android 14+). Fixed in step 5F (see the list of changes above): the manager's `directBootAware` components would have started the main process before the first unlock. Fixed in step 5G (see the list of changes above): the manager's night-mode setting no longer reaches the rest of the app.
