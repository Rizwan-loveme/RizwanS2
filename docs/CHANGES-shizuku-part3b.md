## Findings that decide 3C - 3H (details in `shizuku/README.md`)
1. Upstream is 11 Gradle projects, not one module: `:manager` (library here), `:server`, `:starter`, `:common`, `:shell` and the API submodule's `:aidl`, `:shared`, `:api`, `:provider`, `:rish`, `:server-shared`. Each becomes `:shizuku-<name>` (the manager is `:shizuku`).
2. `:shell` is an application module whose only product is a `classes.dex` (becomes `assets/rish_shizuku.dex`, read by `ShellTutorialActivity`): it stays an application module, outside the Win11 APK.
3. AutoResConfig cannot run in a library (it throws); MaterialThemeBuilder can; `ShizukuLocales` is now generated by the patch script (42 languages + SYSTEM).
4. The Rikka AppCompat fork has the same class names as `androidx.appcompat`: excluded, the project's stock AppCompat is used (the project mixes 1.6.1 / 1.7.0 / 1.8.0, so a project-wide swap is not safe). One visible effect: the settings menu item sits in the overflow menu.
5. `:mika`'s Maven `dev.rikka.shizuku:*` artifacts clash with our API modules (same namespaces, same classes): they are replaced by our modules when the switch is on (3F; planned for step 7 before).
6. `include(...)` is evaluated before the fetch, so the module build files must be in our repo (`shizuku/modules/<name>/`), not in the fetched checkout.

## Decisions
1. Switch `includeShizuku`, **off** by default (the build stays exactly as before until step 4 / 6 make an installable APK); same style as `includeMika`.
2. Plugin versions only through `pluginManagement { plugins { ... } }` (lazy), not the root `plugins { apply false }` block, so a plugin problem cannot break the normal build.
3. Generate `ShizukuLocales` in the patch script (testable here) instead of in a Gradle task (not testable here).
4. Do not generate `locales_config.xml` and the `resConfig` filter (they belong to the application, not to a library).
